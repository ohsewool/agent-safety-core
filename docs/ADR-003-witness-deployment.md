# ADR-003 · witness 배포 형태 — 벤더를 고르지 않는다

**상태**: 확정 (2026-08-19) · **관련**: `core/witness.py`, `tests/test_witness.py`

## 결정해야 했던 것

체크포인트는 Ed25519로 서명된다. 서명은 위조를 막지만 **재생을 막지 못한다** — 호스트가 예전에 유효하게 서명된 체크포인트를 다시 내밀 수 있고, 갈라진 두 이력이 각각 진짜 서명을 달고 있을 수 있다. 진짜 이력과 다시 쓴 이력을 가르는 것은 **호스트가 손댈 수 없는 곳에 있는 단조 카운터**뿐이다.

`Witness`는 그 카운터를 파일로 모형화해뒀고, docstring은 "배포 시에는 감사 대상 기계 밖에 있어야 한다"고만 적혀 있었다. 무엇으로 할지는 미결이었고 후보는 transparency log / 객체 스토리지 / 제3자였다.

## 결정

**어느 것도 고르지 않는다.** 대신 계약과 적합성 시험을 제공한다.

## 왜

명백해 보이는 다음 걸음은 transparency log 하나를 골라 어댑터를 쓰는 것이었다. 그러지 않은 이유가 셋이다.

**보장의 출처가 잘못 읽힌다.** witness가 지켜야 할 성질은 하나다 — *어떤 로그에 대해 보고하는 최고 sequence가 내려가지 않는다.* 이건 append-only 저장소면 무엇이든 제공한다. 특정 제품을 박아두면 보장이 그 제품에서 오는 것처럼 읽히지만, 실제로는 **카운터가 호스트 통제 밖에 있다는 위상**에서 온다. 제품에 대한 주장과 구조에 대한 주장은 다르다.

**의존이 약관을 탄다.** 이 프로젝트의 중심 보장이 한 회사의 가용성과 요금 정책에 걸리게 된다. 그만큼 단순한 성질을 위해 치를 값이 아니다.

**배포자가 이미 신뢰하는 것이 있다.** 다른 팀이 운영하는 서비스, 버전 관리가 켜진 객체 스토리지, 사내 transparency log — 그중 무엇이든 계약을 만족하면 witness다. 만족하지 못하면 어떤 벤더 이름도 그것을 witness로 만들지 못한다.

## 제공하는 것

```
WitnessPort      메서드 3개. publish / latest_sequence / digest_at
FileWitness      로컬 파일. 위협 모형상 witness가 아니다 — 감사 대상 기계 위에 있다.
                 이름을 그렇게 지은 이유는, 이걸 고르는 것이 기본값이 아니라
                 눈에 보이는 결정이 되게 하기 위해서다.
HttpWitness      네 줄짜리 계약을 지키는 아무 엔드포인트. 특정 제공자를 요구하지 않는다.
assert_conforms  배포자가 가져온 것을 실제로 시험한다.
```

## 두 가지 세부 결정

**클라이언트는 단조성을 강제하지 않는다.** `HttpWitness.publish`는 sequence를 검사하지 않고 서버의 409에 의존한다. 클라이언트에서 검사하면 **불변식이 감사 대상 기계 위에서 지켜지는 셈**이고, 그건 이 메커니즘 전체가 피하려는 배치다. 지켜지는 것처럼 보이면서 공격자가 이미 서 있는 자리에 놓는 것이라 위안일 뿐 통제가 아니다.

**도달 불가는 동의가 아니다.** witness에 닿지 못하면 `WitnessError`를 낸다. "응답이 없으니 이의 없음"으로 처리하면 **호스트가 곤란해진 바로 그 순간에 검사가 사라진다** — 가장 필요한 때다.

## 적합성 시험이 실패할 수 있는가

통과만 시키는 시험은 아무것도 증명하지 않는다. `tests/test_witness.py`는 부적합 구현 다섯 종을 만들어 `assert_conforms`가 각각을 거부하는지 확인한다: 반복 sequence를 받는 것, 기록을 잊는 것, 과거 digest를 바꾸는 것, 없는 기록을 지어내는 것, 본 적 없는 로그에 답하는 것.

그중 하나는 실제 배포 실수를 겨냥한다 — **단조성을 강제하지 않는 평범한 key-value 저장소를 witness라고 가리킨 경우.** HTTP 적합성 시험이 그걸 잡는다.

## 남는 것

계약을 만족하는 참조 서버는 제공하지 않는다. 네 줄이라 각 배포가 자기 인프라 위에 얹는 편이 낫고, 참조 구현을 두면 그것이 사실상의 벤더가 되어 이 결정이 무의미해진다.
